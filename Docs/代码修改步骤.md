## 二、必须先知道的一个真相：`LoadTemlateConfig` 不会返回 null

实测（`Ref\DomainAOI.DataExport.dll` + 现场配置目录）：

| ConfigCode | 参数数量 | 首个 Code |
|---|---|---|
| `DefaultMES.SCR`（文件不存在） | **1** | `EnCode` |
| `NOT_EXIST_XYZ_123` | **1** | `EnCode` |
| `""`（空串） | **1** | `EnCode` |
| `DefaultMES` | 65 | `EnCode` |
| `Standard` | 11 | `EnCode` |
| `VIETNAM_ENVADA` | 86 | `EnCode` |

也就是说：**传一个不存在的 ConfigCode，插件不报错、不返回 null，而是返回一个只含 `EnCode` 一项的空壳 `TemplateConfig`**（`JudgeResultSetting` / `DefectTypeSetting` / `Templates` 还都是非 null 的默认对象，所以更隐蔽）。

后果很严重：如果只判 `!= null`，`ResolveConfigCode` 会选中 `DefaultMES.SCR`（DLL 文件名去扩展名），注入就落在一个空壳上——64 个参数全变"新增"，插件后续调用读到的是残缺配置。

**已修复**：`ResolveConfigCode` 改用 `IsUsableConfig`，判据是 `TemplateParamSettings.Count > 1`；`Inject` 里加载基准后也做同样校验，不通过直接抛异常并说明原因。

> 这也更正了之前文档里"`DefaultMES.SCR` 失败 → `DefaultMES` 成功"的说法：它不是失败，是**静默返回空壳**。

## 三、`ConfigInjector` 的六个步骤

```
① ResolveConfigCode        按 count>1 选基准，选中 DefaultMES
② LoadTemlateConfig(Code)  走插件自己的解析（含解密、IsUserEdit、判重）
③ 遍历 XML Entries         命中 → SetValue；属性表有但配置无 → 新增；都没有 → Unknown
③.5 全不匹配告警           applied=0 && added=0 && unknown>0 → 提示 ConfigPath 可能指错
④ 写 BaseParams._InConfig  唯一注入点（private static，非 readonly）
⑤ 回读校验                 InParams.Xxx 读回来是否等于写入值 → VerifyFailed
```

`Success` 只看 `VerifyFailed`。**`Unknown` 永远不阻断执行**，只进日志。

日志最多显示：改值/新增 20 条、未识别/校验失败 10 条、提示 5 条，超出显示 `… 等 N 项`。

## 四、`Form1.cs` 里加了注入的四个位置

| 方法 | 说明 |
|---|---|
| `btnCreateConfig_Click` | 独立"注入"按钮（原来的空方法） |
| `btnBarCodeCheck_Click` | 调用前注入 |
| `btnGetBadMark_Click` | 调用前注入 |
| `MesOutPut_Click` | 调用前注入（并补了 `SelectDll` 校验） |
| `btnSendDataForDefaultMES_Click` | 调用前注入（并补了 `SelectDll` 校验） |

统一写法：

```csharp
InjectResult inject = ConfigInjector.Inject(XmlConfigServer.LoadFromIni(), SelectDll);
AppendLog(inject.Message);

if (inject.HasUnknown)
    AppendLog(inject.Detail());          // 有未识别项打明细，但不 return

if (!inject.Success)                     // 只有回读校验失败才中止
{
    AppendLog("[注入] 回读校验未通过，已中止调用：" + inject.Detail());
    return;
}
```

**为什么每个方法都注入一次、而不是启动时注一次**：插件内部的 `RefreshConfig()` 会清 `_ConfigName` 并按文件名重新读盘，注入的值会被冲回文件里的值。必须紧贴调用。

## 五、为什么 `config.ini` 改指向副本

原来指向 `D:\EYAOI\MesCustom\Bin\Config\Setting\DefaultMES.config`，那正是 `LoadTemlateConfig("DefaultMES")` 读的同一个文件——**用现场值覆盖现场值，`改值` 永远是 0**，验证不出任何东西。

现在指向副本：

```ini
[Server]
ConfigPath = Config\TestXml\aoi_test.config
ModelTpye=AOI
AOIDllPath=D:\EYAOI\MesCustom\Bin\CustomDLL
SPIDllPath=D:\EYSPI\Bin\CustomDLL
```

副本已经把 `MachineName` 改成 `AOITEST-INJECT`（现场仍是 `MI6071`），所以第一次跑就能看到 `改值=1`。

相对路径按 `AppDomain.CurrentDomain.BaseDirectory` 解析，不依赖进程工作目录。

1. **重启 AOITest**（`Form1_Load` 才重读 `config.ini`）
2. `ModelType` 选 AOI，DLL 选 `DefaultMES.SCR`
3. 点注入按钮 → 日志应出现：


   同时弹窗提示注入成功。
4. 点 `GetBadMark` → 日志先打注入摘要，再打插件返回值

   `"MachineName":"AOITEST-INJECT"` —— 这就是"外部 XML 的值真的进了请求体"的铁证

   `<Setting Code="MachineNameXX" Name="x" IsUserEdit="1">x</Setting>`
   → 注入显示 `未识别=1`，日志多一行 `[注入] 未识别（已跳过，继续执行）：MachineNameXX`，
   不弹错误框；接着点 `GetBadMark` 仍能正常调用完

## 八、已知风险

1. **SPI 模式可能跑不了。** 代码强类型引用 `DomainAOI.DataExport`（Ref 那份，AOI 版）。SPI 插件依赖同名另一份，运行时可能 `MissingMethodException`。先只在 AOI 上验。
2. **AOI / SPI 不能同进程来回切。** 两套 `SinicTek.SDK` 同名不同构建，CLR 先加载者胜。切机型必须重启。
3. **`RefreshConfig()` 会冲掉注入**，所以注入必须紧贴调用。
4. **`App.InConfig` / `App.InConfigName` 都不要用。** 前者插件根本不读，后者会写盘污染现场设置。
5. **本机编译验证不了**（`csc.exe` / `MSBuild.exe` 被安全策略拦）。已做的是：逐行审查 + 括号/字符串词法扫描 + PowerShell 跑等价注入逻辑。第一次编译若报语法错请把报错发我。
6. **`ExportDataPathRule-1 / -2` 仍然取不到值。** 模板里是带横杠的名字，`InParams` 属性是 `ExportDataPathRule1/2`。这两个 Code 在 XML 和基准配置里都存在（名字一致），所以注入器不会报 Unknown——问题在插件自身的"属性名 → Code 名"映射上，属于模板 bug，注入器无法修正。
