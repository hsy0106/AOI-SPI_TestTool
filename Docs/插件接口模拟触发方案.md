# AOI/SPI 自定义插件 —— MES 接口"模拟触发"结构方案

> 分析对象：`D:\EYAOI\MesCustom\Bin\CustomDLL\DefaultMES\DefaultMES.SCR.dll`（AOI）
> `D:\EYSPI\Bin\CustomDLL\SHENZHEN_TWSC\SHENZHEN_TWSC.SPISCR.dll`（SPI）
> 分析方式：反射取元数据 + IL 常量扫描（不是猜的，下面的"接口段"是 DLL 里真实存在的字符串常量）
> 现有测试器：`AOITest` 项目

---

## 一、先把事实摊开：这些 DLL 里到底有什么

### 1.1 两个插件的入口类

| 机型 | DLL | 入口类 |
|---|---|---|
| AOI | DefaultMES.SCR.dll | `SpecialCaseRun.AOI` |
| SPI | SHENZHEN_TWSC.SPISCR.dll | `SpecialCaseRun.SPI` |

两个类的结构套路完全一样：**一个 public 入口方法 → 拼 XxxRequestInfo 对象 → JsonConvert → HttpPost → 解析回包 XxxResponseInfo → 返回 ESResult**。

DLL 里还有一整套 `XxxRequestInfo / XxxResponseInfo` 实体类（`SpecialCaseRun.BarCodeCheckRequestInfo` 等），
这些就是"接口要传的参数清单"最权威的定义，不需要问对方要文档。

### 1.2 会真正往外发 HTTP 的方法（AOI）

| 入口方法 | 方法签名 | 请求接口段 | 请求体实体 |
|---|---|---|---|
| LoginCheck | `ESResult LoginCheck(AppSetting)` | `/LoginCheck` | LoginCheckRequestInfo |
| BarCodeCheck | `ESResult BarCodeCheck(BarCodeTree, CST)` | `/BarCodeCheck` | BarCodeCheckRequestInfo |
| GetArrayBarCodesForHttp | `ESResult GetArrayBarCodesForHttp(BarCodeTree)` | `/GetBarCode` | GetBarCodeRequestInfo |
| GetArrayBarCodes | `ESResult GetArrayBarCodes(BarCodeTree)` | **不走网络**，读本地 `BoardInfo_*.stf` | — |
| GetBadMark | `ESResult GetBadMark(BarCodeTree, CST)` | `/GetBadMark` | GetBadMarkRequsestInfo |
| MesOutPut | `ESResult MesOutPut(BoardPCB)` | `/MesOutPut` | MesOutPutRequestInfo |
| SendDataForDefaultMES | `ESResult SendDataForDefaultMES(BoardPCB)`（**private**） | `/MesOutPut` | 默认 MES 文本格式 |
| UISystemState | `ESResult UISystemState(ushort lane, DateTime, string state, string errCode, string errMsg)` | `/UpdateDeviceStatus` | UpdateDeviceStatusRequestInfo |
| JobLoaded | `ESResult JobLoaded(ushort, string, CL_DATA_Job, Dictionary<string,object>)` | Job 切换 | SwitchJobInfo |
| SystemStart | `ESResult SystemStart()` | 启动时自检（含 LoginCheck） | — |

`SwitchJob` 方向相反：**插件当服务端**，用 `IsEnableWebApiServer` / `WebApiServerUrl` 起 HttpListener，收 `/SwitchJob`、`/DevCmd`。

### 1.3 会真正往外发 HTTP 的方法（SPI）

| 入口方法 | 请求接口段 | 备注 |
|---|---|---|
| LoginCheck(AppSetting) | `/LoginCheck` | |
| ParamsCheck(AppSetting) | `/ParamsCheck` | **AOI 没有这个方法**，SPI 独有 |
| BarCodeCheck(BarCodeTree, CST) | `/BarCodeCheck` | 内部走 `OnlyBarCodeCheck` |
| GetBadMark(BarCodeTree, CST) | `/GetBadMark` | |
| MesOutPut(BoardPCB, CST) | `/MesOutPut` | 另外还会传 CPK |
| SendDataForDefaultMES(BoardPCB) | `/MesOutPut` | 整板/全局 Mark 组两种模式 |
| StatusNotification(SystemEquipmentStatus) | `/EquipStatus` | 单次状态上报 |
| PutStateRecord(List<...>) | `/UpdateDeviceStatus` | 状态记录批量上报 |
| HttpReceiveRequest(url, query, post) | 被动接收 `/DevCmd`、`/SwitchJob` | 插件当服务端 |
| MessageHandle(object) | 不联网 | UI 消息分发：`JobLoad` / `SwitchJob` / `IsStopCheck` / `MesChange` / `MesCustomerButton` |
| Start/Run/StopEquipStatusThread() | `/EquipStatus` | 心跳线程，**有副作用**，不要随手触发 |

### 1.4 参数只有三种来源

1. **XML 配置**（`<TemplateParam><Setting Code="xxx">值</Setting>`）
   AOI 在 `D:\EYAOI\MesCustom\Bin\Config\Setting\<ConfigName>.config`
   SPI 在 `D:\EYSPI\Bin\Config\Setting\<ConfigName>.config`
2. **IL/板卡数据 json**（`AOITest\bin\Debug\IL\*.json` → `IlPcbResult` → `BoardPCB`）
3. **运行时 SDK 对象**（`AppSetting`、`CST`、`SystemEquipmentStatus`、`CL_DATA_Job`），这几类 XML 里没有，必须 new 出来。

### 1.5 每个接口字段 ← 配置项 对照（这是"造参数"的说明书）

**LoginCheckRequestInfo**

| 字段 | 来源 |
|---|---|
| MachineID | XML `MachineID` |
| MachineName | XML `MachineName` |
| SoftName / SoftVersion | XML `SoftName` / `SoftVersion` |
| Operator | XML `Operator` |
| LineName | XML `LineName1`（1轨）/ `LineName2`（2轨），按 `BoardPCB.LaneNo` 选 |
| IP / Mac | XML `IP` / `Mac`（也可用本机真实值覆盖） |

**BarCodeCheckRequestInfo**

| 字段 | 来源 |
|---|---|
| BarCode | IL json `PCB.PCBBarcode`，或界面手填 |
| CarrierBarcode | IL json `PCB.CarrierBarcode` |
| WorkNo | XML `WorkNo1` / `WorkNo2` |
| Operator / JobName / LineName / WorkStation | XML `Operator` / `PCB.JobName` / `LineName1|2` / `WorkStation1|2` |
| GroupBarCode[] / ArrayBarCode[] | IL json `PCB.ArrayGroups` / `PCB.ArrayPCBs` |

**GetBadMarkRequsestInfo**：同上 + `Side` ← XML `Side1` / `Side2`（按板面）。
**MesOutPutRequestInfo**：`BoardStatus` 由 `PCB.Result` 映射（JudgeRes 段），`DateTime` ← `PCB.StartTime`，`Array` ← `PCB.ArrayPCBs` 逐个转换。
**UpdateDeviceStatusRequestInfo**：`StatusCode` 来自状态机（`Start/Run/Stop/Error/Idle`），`ErrorList` 是 `ErrorListItem{ErrorCode,ErrorMessage,SuggestedSolutions}`。

> 结论：**参数不是"随便造的"，是"配置项 + 板卡数据 + 状态"的确定性映射**。所以方案的核心是把这个映射显式化、可编辑，而不是每个按钮里写死一段 new。

## 二、现在的结构卡在哪

对照 `AOITest\Form1.cs` 现状：

1. **枚举 + 一个方法一个按钮**（`Enum\AOIMethod.cs` + 8 个 Click 处理器）
   加一个方法就要改枚举、改 Designer、改 handler，参数逻辑散落在各 handler 里。
   `LoginCheck_Click` 甚至是空的，`btnGetBarCodeResult_Click` 也是空的。

2. **参数硬编码在 handler 里**
   `BarCodeCheck_Click` 里 `LaneNo = 1`、`ExtendBarcode = ""`、`JobNum = "1"` 写死；
   `BuildMockMessageParam` 里 fallback 是 `"WO-TEST-0001"`、`"admin"`、`"LINE-1"`。
   改一个字段要重编译。

3. **`DllMethodInvoker` 只认「参数个数 + 类型完全匹配」的 public 方法**
   - `AppSetting` / `CST` / `BarCodeTree` 这类对象传不进去（没有工厂）；
   - `SendDataForDefaultMES` 在 AOI 和 SPI 里都是 **private**，现在按钮点了必然 `MissingMethodException`；
   - 不传 private → 一半方法根本触发不了。

4. **没有 MES 端**
   `InterfaceUrl` 指向 `http://127.0.0.1:7070/`，本机没服务 → 插件 POST 直接异常。
   你只能看到"异常"，看不到"它到底传了什么参数"——这恰恰是最需要看的东西。
   （另外 `SHENZHEN_TWSC.config` 里 `InterfaceUrl = http://127.0.0.1/9020` 端口写成了路径，本身就是错的。）

5. **配置是进程级单例**
   `BaseParams.ConfigName` + `static RefreshConfig()`，切 XML 不刷新会读到旧值；`AppSetting.ConfigCode` 决定了插件去 `Config\Setting\` 下找哪个 `.config`。

## 三、建议结构：五层，一层一件事

```
┌──────────────────────────────────────────────────────────────┐
│ L4  Scenario  场景编排（登录→条码→BadMark→过站→导出）           │
├──────────────────────────────────────────────────────────────┤
│ L0  TriggerCatalog  方法目录（表驱动，不再用 enum）             │
│     Id | 类名 | 方法名 | 参数工厂 | 接口段 | 依赖配置 | 备注     │
├──────────────────────────────────────────────────────────────┤
│ L1  Fixtures  参数工厂（4 类）                                 │
│     XmlFixture → AppSetting / InParams                        │
│     PcbFixture → BoardPCB / BarCodeTree（IL json）             │
│     RuntimeFixture → CST / SystemEquipmentStatus / List<>      │
│     RawFixture → Dictionary（MessageHandle / HttpReceive）      │
├──────────────────────────────────────────────────────────────┤
│ L2  Invoker  调用 + 记录（支持 private / 类型转换 / 实例复用）   │
├──────────────────────────────────────────────────────────────┤
│ L3  MockMesServer  录制 + 应答（HttpListener 127.0.0.1:7070）   │
└──────────────────────────────────────────────────────────────┘
```

### L0 TriggerCatalog —— 用"一张表"替掉 enum

```csharp
public class TriggerDescriptor
{
    public string Id;                 // "LoginCheck"
    public string ClassName;          // "SpecialCaseRun.AOI" / "SpecialCaseRun.SPI"
    public string MethodName;         // "LoginCheck"
    public string[] ParamKinds;       // { "AppSetting" } —— 与 ParamFactory 注册名对齐
    public string UrlSegment;         // "LoginCheck" —— MockServer 用来路由/高亮
    public string[] ConfigKeys;       // { "MachineID","MachineName",... } —— 界面上提示"这条要用哪些配置"
    public string Shape;              // "LoginCheckRequestInfo" —— 展示用
    public bool HasSideEffect;        // 心跳线程/写文件 → 二次确认
    public string Note;
}
```

初始化分两步：
1. **反射自动扫**：`asm.GetTypes()` → `SpecialCaseRun.*` → 所有 `public/private` 方法 → 生成候选行（Id = 方法名）。这样将来客户换插件版本、方法增减，界面自动跟着变，不用改代码。
2. **本地覆盖表**：手工补 `ParamKinds` / `UrlSegment` / `ConfigKeys`（`TriggerCatalog.Overrides.cs`，一个静态字典）。

界面上就是 `DataGridView` 一行一个方法：`方法名 | 参数(只读) | 接口段 | 依赖配置 | 状态 | 备注`，双击行 → 弹出该方法的**参数编辑面板**（根据 ParamKinds 动态生成）。

### L1 Fixtures —— 参数工厂，把 1.5 节那张对照表变成代码

```csharp
public interface IParamFactory
{
    string Kind { get; }                       // "AppSetting" / "BoardPCB" / "BarCodeTree" / "CST" ...
    Type ParamType { get; }
    object Create(TriggerContext ctx);         // 从 ctx 里取 XML / IL / 手工覆盖值
}
```

核心是 `TriggerContext`——它就是"所有可编辑输入的集合"，界面改什么都改这里，工厂只从这里取：

```csharp
public class TriggerContext
{
    public XmlConfigServer Config;             // XML 配置（可编辑后回写 Values 覆盖）
    public Dictionary<string,string> Overrides; // 界面手工覆盖：键 = 配置 Code 或字段名
    public IlPcbResult Il;                     // IL json
    public string LaneNo;                      // "0"/"1"
    public BoardPCB Pcb;                       // 由 Il 转换 + Overrides 修正
    public CST Trace;                          // new CST{ TraceID=1, StartTime=Now, ... }
    public ESResult Run(TriggerDescriptor d);
}
```

典型实现（`AppSettingFactory`）：

```csharp
public object Create(TriggerContext ctx)
{
    return new AppSetting
    {
        ConfigCode = ctx.Overrides.Get("ConfigCode", ctx.Config.ConfigName), // ← 关键：等于 Setting 目录下的 .config 文件名
        LineName   = ctx.Overrides.Get("LineName",  ctx.Config.GetValue("LineName1")),
        WorkNo     = ctx.Overrides.Get("WorkNo",    ctx.Config.GetValue("WorkNo1")),
        Operator   = ctx.Overrides.Get("Operator",  ctx.Config.GetValue("Operator")),
    };
}
```

`BoardPCB` / `BarCodeTree` 工厂沿用现在 `Form1.cs` 里已经写好的那段（`IlPcbResult → BoardPCB`、`BarCodeTree{...}`），
只是把硬编码的 `LaneNo=1 / JobNum="1"` 换成 `ctx` 里的可编辑值。

> **为什么值得这么拆**：参数一多（BarCodeCheck 有 10 个字段），只靠按钮 + 重编译必然失控；
> 拆成"上下文 + 工厂"后，界面上加一个输入框就等于加一个可模拟参数，不用碰调用逻辑。

### L2 Invoker —— 修 `DllMethodInvoker` 的四个硬伤

| 现状 | 改成 |
|---|---|
| 只找 `BindingFlags.Public` | 加 `NonPublic`（`SendDataForDefaultMES` 等 private 方法要能打） |
| 类型必须 `IsInstanceOfType` 完全匹配 | 加 `Convert.ChangeType` 兜底（string→int/DateTime/enum），null 容忍引用类型 |
| 每次 `Activator.CreateInstance` | 按 `(dll, className)` 缓存实例（插件有字段状态和线程，反复 new 会打架） |
| 只返回结果 | 返回 `TriggerResult{ 入参JSON, 返回值, 耗时, 异常, 期间HTTP抓包 }` |

另外建议加一个"**dry-run**"开关：只构造参数不调用，把参数 JSON 打在日志里 —— 先确认参数对不对，再真正发。

### L3 MockMesServer —— 这一层是"模拟触发"的灵魂

> 你的问题本质是"**怎么模拟触发这些接口**"。
> 答案不是"假装调一下"，而是**在 127.0.0.1 起一个假 MES**，让插件真的发请求出去，你把它收下来。
> 这样既完成了"触发"，又拿到了"它到底传了什么参数"。

```
插件 ──POST /LoginCheck──▶ MockMesServer ──▶ ① 记录请求（path + body + header + 时间）
        (InterfaceUrl)          │              ② 按路由返回预置 JSON
                                └──▶ ③ 界面可见 + 落盘 Req_yyyyMMddHHmmss_LoginCheck.json
```

要点：

```csharp
var listener = new HttpListener();
listener.Prefixes.Add("http://127.0.0.1:7070/");   // 必须是 127.0.0.1 而不是 +，否则要管理员权限
listener.Start();
// 按 path 分发：/LoginCheck /BarCodeCheck /GetBarCode /GetBadMark /MesOutPut
//              /ParamsCheck /UpdateDeviceStatus /EquipStatus /SwitchJob
```

**路由表用文件驱动**，不要写死在代码里：

```
MockResponses/
  LoginCheck.json            { "Result":"OK", "EventCode":0, "Message":"ok" }
  BarCodeCheck_OK.json       { "Result":"OK", "EventCode":0, "Message":"ok", "JobName":"TEST-JOB" }
  BarCodeCheck_NG.json       { "Result":"NG", "EventCode":1, "Message":"barcode not found" }
  GetBarCode.json            { "Result":"OK","EventCode":"0","GroupBarCode":["G1"],"ArrayBarCode":["A1","A2"] }
  GetBadMark.json            { "Result":"OK","EventCode":0,"Message":"ok","ArrayBarCode":["A1"] }
  MesOutPut.json             { "Result":"OK","EventCode":0,"Message":"ok" }
  UpdateDeviceStatus.json    { "Result":"OK","EventCode":0,"Message":"ok" }
```

界面上每个接口一行：`接口段 | 当前应答文件 | 场景(OK/NG/空/超时/异常) | 最近一次请求体`。
切换"场景"就是换一个 json → 插件的 `GetXxxResult` 走不同分支，**这才是真正的"模拟"**。

配套注意：
- 超时场景：Sleep 到超过 XML 的 `Timeout`（4s），验证插件超时逻辑。
- 空回包场景：返回 `""`，验证 `不能识别的返回字符串:` 分支。
- 异常场景：直接 500，验证 `接口异常:` 分支。

### L4 Scenario —— 把单点触发串成流程

```csharp
var steps = new[] {
    "LoginCheck",
    "GetArrayBarCodesForHttp",
    "BarCodeCheck",
    "GetBadMark",
    "MesOutPut",
    "UISystemState:Start",
};
```

一步步执行，每步：造参数 → 触发 → 抓请求 → 断言回包字段。
输出一张"链路表"：哪一步没发请求、哪一步回包解析失败，一眼看到断点。
（`DataSimConfig.json` / `BatchNoStateL1.json` 在 `D:\EYAOI\Bin\Config\` 下，可以参考现场批量模拟的做法。）

## 四、几个必须踩对的细节

1. **`AppSetting.ConfigCode` = `Config\Setting\` 下的文件名（不含扩展名），不是随便起的名字**
   - AOI：`DefaultMES.config` / `VIETNAM_ENVADA.config` → `ConfigCode = "DefaultMES"`
   - SPI：`ConfigName` 实际取自 `Env.ProjectName`，而 `Env.ProjectName` = **DLL 名**，
     所以必须是 `SHENZHEN_TWSC.SPISCR.config`（不是 `SHENZHEN_TWSC.config`）。
   传错/文件不存在 → `DomainSPI.MES.App.LoadTemlateConfig` 返回 null →
   `get_Config` 抛 `"SPI配置文件不存在或读取失败"` → 被插件自己的 catch 吞掉 → 表现为"点了没反应"。
   这个坑已经踩过一次（见 `.workbuddy/memory/2026-10-20.md`）。

2. **`BaseParams.RefreshConfig()` 是 static**
   界面改了 XML 参数后必须调一次刷新，否则插件还用着第一次加载的 `TemplateConfig`。

3. **`InterfaceUrl` 结尾的 `/`**
   插件拼法是 `InterfaceUrl + 接口段`，`http://127.0.0.1:7070/` 正确；
   `SHENZHEN_TWSC.config` 里 `http://127.0.0.1/9020` 会拼成 `http://127.0.0.1/9020LoginCheck`，必错。

4. **`CST` 先给最小对象**
   `new CST { TraceID = 1, EventID = 1, StartTime = DateTime.Now, LaneNo = "1", BarCode = pcb.BarCode }`。
   如果插件内部用 `LastNode`/`EventNodes` 写 trace 时炸了，再补 `SetEvent`。
   建议：调用前先传 `null` 试一次（多数实现会判空），不行再给对象。

5. **有副作用的方法单独标红**
   `StartEquipStatusThread` / `RunEquipStatusThread` 会起线程持续打 `/EquipStatus`；
   `MesOutPut` 会往 `D:\EYAOI\DataExport` 写文件/CSV。
   这类方法在 Catalog 里 `HasSideEffect = true`，执行前弹确认。

6. **x64**
   `AOITest.csproj` 是 `PlatformTarget=x64`，而插件依赖 `SQLite.Interop.dll` 等原生库；
   加载客户 DLL 时目录里必须能解析到这些依赖（现在 `DllTool` 里被注释掉的 `AssemblyResolve` 那套逻辑就是解决这个的，建议恢复成可用版本）。

## 六、AOI 与 SPI 不能同进程（这条决定了测试器的骨架）

实测：`Ref\SinicTek.SDK.dll` 存在**两套同名同版本（1.0.0.0，无强名）但类型成员完全不同**的构建：

| | AOI 版 | SPI 版 |
|---|---|---|
| 位宽 | PE32+ x64，72KB | PE32 AnyCPU，98KB |
| 主命名空间 | `SinicTekAOI.SDK`(22) | `SinicTekSPI.SDK`(10) + `SinicTek.SDK`(28) |
| `BoardPCB` 成员数 | 13 | 161 |
| 独有 | `ComponentSpec` / `ComponentWindow` / `DefectResult` | `Pad` / `PadSetting` / `SystemEquipmentStatus` / `BarCodeTree` |

同标识程序集无法在一个 AppDomain 里共存，CLR **先加载者胜**。
所以：

- `TriggerCatalog` 必须带 `ModelType` 维度，`AppSetting`/`BoardPCB` 工厂也要分 AOI / SPI 两套实现；
- 切机型时**必须重启进程**（或 `AppDomain.CreateDomain` 隔离），不能热切换；
- 现在 `config.ini` 里 `ModelTpye=AOI` 但 `ConfigPath` 指向 SPI 的 `SHENZHEN_TWSC.config`，本身就是混的，先统一。

这条不解决，后面无论怎么设计参数工厂，都会随机爆 `TypeLoadException` / `MissingMethodException`。

## 七、落地顺序（每步都能单独验证）


| 步 | 做什么 | 验证标准 |
|---|---|---|
| 1 | 起 `MockMesServer`（只要录制 + 固定 OK 应答），把 XML `InterfaceUrl` 指向它 | 点 `BarCodeCheck` 按钮，能在服务端看到完整 JSON body —— 这一步就能立刻回答"它传了什么" |
| 2 | 给 `DllMethodInvoker` 加 private + 类型转换 + 实例缓存 | `SendDataForDefaultMES`、`UISystemState` 能触发（原来打不通的） |
| 3 | 抽 `TriggerContext` + 4 个 ParamFactory，`Form1` 改成"一行一次触发" | `BarCodeCheck` 的 10 个字段能在界面上逐个改 |
| 4 | 上 `TriggerCatalog` 表驱动 + 参数面板动态生成 | 新增方法零改代码（反射自动出现一行） |
| 5 | 场景编排 + 断言 + 链路表 | 一条命令跑完 登录→条码→过站→导出 |
