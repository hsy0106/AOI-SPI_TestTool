# AOITest 客户参数契约设计（以 DefaultMES 打样）

> 目标：让 AOITest 能说清"这次调用我会给过去哪些数据、每个数据从哪来"，并提前发现 XML 与插件字段对不上。
> 本文只做设计，不含实现。

---

## 0. 一句话结论

**不要在 AOITest 里重造"XML → InParams"的映射。** 插件里 `SpecialCaseRun.InParams` 的每个属性本身
就是一次"按属性名去 XML 里查值"的动作，映射关系是插件内部固化的。AOITest 要做的是两件事：

1. **校验这个约定成立**（XML 的 `Code` 集合 vs `InParams` 的属性集合）；
2. **把每个接口真正消费的客户参数摊开**（哪些字段来自 XML、哪些来自运行时对象）。

---

## 1. 已验证的机制（反编译 + IL 实测，非推测）

### 1.1 InParams 是"活查表"，不是数据容器

`SpecialCaseRun.InParams`：**64 个属性，全部 static，全部只读，没有 setter**。

实测 `InParams.MachineName` 的 getter IL：

```
[call]     BaseParams.get_InConfig
[callvirt] TemplateConfig.get_TemplateParamSettings
[call]     DevelopService.GetValue
```

等价于插件里的写法：

```csharp
public static string MachineName =>
    DevelopService.GetValue(BaseParams.InConfig.TemplateParamSettings, "MachineName");
```

`IsReadBadMarkFile` 多一步：

```
[call]     DevelopService.GetValue
[call]     String.op_Equality
```

即 `... == "1"`。

**推论**：
- 属性名 **必须** 与 XML 的 `Code` 完全相等（大小写敏感、不能有横杠差异）；
- 没有任何"额外参数注入"的口子 —— 想让某个客户参数变化，只能改 XML 里对应的 `Code` 的值。

### 1.2 唯一的注入点：`BaseParams._InConfig`（惰性加载）

ildasm 实证的三个成员：

```csharp
public static string ConfigName {
    get {
        if (string.IsNullOrEmpty(_ConfigName))
            _ConfigName = App.InConfigName;        // ← 从 App.InConfigName 取
        return _ConfigName;
    }
}

public static TemplateConfig InConfig {
    get {
        if (_InConfig == null)
            _InConfig = DevelopService.LoadTemlateConfig(ConfigName);
        return _InConfig;
    }
}

public static void RefreshConfig() {
    _ConfigName = string.Empty;                    // ← 先清空
    _InConfig = DevelopService.LoadTemlateConfig(ConfigName);   // getter 再从 App.InConfigName 取
}
```

`_ConfigName` / `_InConfig` 是 `private static`，**且不是 readonly**（可反射写）。

由此得出三条硬规则：

| 规则 | 原因 |
|---|---|
| `App.InConfig` 有 public setter，但**设它没用** | `BaseParams` 的懒加载走 `App.InConfigName` → 重新 `LoadTemlateConfig`，从不读 `App.InConfig` |
| `App.InConfigName` 有 public setter，但**有副作用** | 它的 IL 末尾会调 `MesSettingService.GetSettings` + `MesSetting.set_CurrentConfig` + `SaveSettings`，即**把"当前激活配置"持久化写进现场设置** |
| `_ConfigName` 有缓存 | 进程内首次访问后就固定。换配置必须 `RefreshConfig()`（它先清空再重载） |

**结论**：AOITest 不需要逐个字段赋值，只需要让 `BaseParams._InConfig` 指向一份 `TemplateConfig`，
64 个客户参数自动全部到位。推荐注入方式见 1.8。

### 1.2.1 `ParamSetting` 特性 vs `TemplateParamSetting`

`InParams` 的每个属性上都挂着特性（反射实测）：

```
[ParamSetting(Code="MachineName", Name="设备名称", DefaultValue="MI6071", IsUserEdit=True)]
```

`ParamSettingAttribute` 的成员：`Code` / `Name` / `DefaultValue` / `IsUserEdit`
`TemplateParamSetting` 的属性：`Code` / `Name` / `Value` / `IsUserEdit`

**四对四一一对应**。所以插件的设计意图是：

```
特性描述模板（默认值/显示名/是否可编辑）
        → XML 存值（<Setting Code="..." Name="...">值</Setting>）
        → TemplateParamSetting 承载（Value = XML 里的值）
        → InParams 只读查到（按 Code 匹配）
        → 请求实体 set_XXX
```

**这直接回答了"能不能把外部 XML 转化到 InParams 类"：不能，也不需要。**
`InParams` 的 64 个属性 **writable = 0**（全是只读表达式属性，没有 setter，也没有 backing field），
`new InParams()` 只是个空壳，而 `GetBadMark` 调用的是**静态**的 `InParams.Xxx`，不接收实例。

真正要"转化"的目标是 **`TemplateConfig.TemplateParamSettings`**。

### 1.3 bool 只认字面量 `"1"`

判定式是 `GetValue(...) == "1"`。所以：

| XML 里写的值 | 插件读到的 bool |
|---|---|
| `1` | `true` |
| `0` | `false` |
| `true` / `True` / `yes` / `是` / 空 | **`false`（静默）** |

这是最容易踩的坑：XML 里写 `true`，不看代码会以为开关开了，实际是关的，方法直接 return，表现为"点了没反应"。

### 1.4 配置目录是**硬编码**的（此处更正早期判断）

`CommonSystemConfig` 的两个 getter 用 ildasm 看到的都是**字面量**，不是运行时算出来的：

```csharp
public static string ConfigBaseDirPath          => "D:\\EYAOI\\Bin\\Config\\IL";
public static string MesCustomConfigBaseDirPath => Path.Combine("D:\\EYAOI\\MesCustom\\Bin\\Config", "Setting");
public static string OldMesCustomConfigBaseDirPath => Path.Combine("D:\\EYAOI\\Bin\\Config", "Setting");
```

即插件永远读 **`D:\EYAOI\MesCustom\Bin\Config\Setting\{ConfigCode}.config`**，与 AOITest 装在哪里无关。

两层含义：

- **好消息**：AOITest 不需要在自己 `bin\Debug` 下铺一份配置，它读到的就是现场真实配置，最贴近实况；
- **约束**：路径写死，所以**绝对不要改现场已有文件**。要做实验配置就**新增**文件
  （如 `...\Setting\AOITest.config`），再用 1.8 的方式注入。

副作用：这台机器上必须有 `D:\EYAOI\...`，否则 `LoadTemlateConfig` 读不到，`_InConfig` 为 `null`，
`InParams.Xxx` 取属性时直接 `NullReferenceException`（被插件自己的 try/catch 吞成一句"异常"）。

### 1.8 推荐注入方式（3 行，零副作用）

绕开 `App`，直接用公开的 `DevelopService.LoadTemlateConfig` + 反射写私有静态字段：

```
1) var cfg = DevelopService.LoadTemlateConfig("DefaultMES");      // 只读文件，无副作用
2) typeof(BaseParams).GetField("_InConfig", BindingFlags.NonPublic | BindingFlags.Static)
                     .SetValue(null, cfg);
3) 之后 InParams.MachineName / GetBadMark(...) 用的就是这份 XML 的值
```

这样做避开了三个坑：不触发 `SaveSettings` 写现场设置、不受 `_ConfigName` 缓存影响、不需要 `RefreshConfig()`。

**"外部 XML"场景怎么接**：`LoadTemlateConfig` 只能读硬编码目录，所以外部 XML 有两条接法：

| 接法 | 做法 | 适用 |
|---|---|---|
| 覆盖值 | 先用 `LoadTemlateConfig` 加载一份基准（保证 `JudgeResultSetting`/`DefectTypeSetting`/`Templates` 不空），再把 `TemplateParamSettings` 里对应 `Code` 的 `Value` 换成外部 XML 的值，然后注入 | **推荐**，其它段完整 |
| 整个替换 | 自己 new `TemplateConfig` + 自己 new `TemplateParamSetting` 列表 | 不推荐，其它段全空，别的接口会 NRE |

改单个值用现成的公开方法即可：`App.SetValue(cfg.TemplateParamSettings, "MachineName", null, "TEST-1234")`。

### 1.5 实测 diff：AOI 的 DefaultMES 模板有 2 处对不上

对 `D:\EYAOI\MesCustom\Bin\Config\Setting\DefaultMES.config` 与 `SpecialCaseRun.InParams` 做集合比对：

```
XML Code 数: 64    InParams 属性数: 64

XML 有 / InParams 无:  ExportDataPathRule-1
                       ExportDataPathRule-2
InParams 有 / XML 无:  ExportDataPathRule1
                       ExportDataPathRule2
```

62 / 64 完全对齐，**剩下两项因为多了个横杠而永远取不到值**。后果是 `ExportDataPathRule1/2`
恒为 `null`，导出路径规则退回默认逻辑。

这不是 AOITest 的 bug，是模板本身的问题 —— 但正是这种问题，光靠肉眼比对 XML 和界面永远发现不了。
**它也是这套校验器存在的最强理由。**

### 1.6 另一条隐藏规则：`IsUserEdit`

`LoadTemlateConfig` 里 `TemplateParamSetting.IsUserEdit` 同样用 `== "1"` 判定。
它决定该项是否出现在现场的"客户参数"编辑界面（`TemplateConfig.IsHasUserEditSetting`）。

对 AOITest 的意义：`IsUserEdit="1"` 的那批 Code，才是客户真正会在现场改的；
其余是设备方配置。**测试时应该优先覆盖 `IsUserEdit="1"` 的项**，因为它们才是变量。

### 1.7 重复 Code 的合并规则

`LoadTemlateConfig` 对每个 `Setting` 先 `Where(...).Any()` 判重，已存在则更新 `Name`/`Value`/`IsUserEdit`，
不存在才 `Add`。即 **同一个 Code 写多次，后者覆盖前者，不会报错**。
校验器可以顺便把这种情况报出来（多半是模板复制粘贴的残留）。

## 2. 三个模块

结构上一共三块，互相独立、可分别交付。

```
        ┌────────────────────────────────────────┐
        │ D:\EYAOI\MesCustom\Bin\Config\Setting\  │  ← 硬编码路径，只读不改
        │            *.config                     │
        └───────────────────┬────────────────────┘
                            │ DevelopService.LoadTemlateConfig(code)
                            ▼
              ┌─────────────────────────────┐
              │  TemplateConfig              │  ← 复用插件自己的解析
              │  .TemplateParamSettings[]    │     （含解密、IsUserEdit 规则）
              └──────────────┬──────────────┘
                             │ 反射写入 BaseParams._InConfig
                             ▼
              ┌─────────────────────────────┐
              │  InParams 64 个静态只读属性   │
              └──────────────┬──────────────┘
                             │
              ┌──────────────┼─────────────────────┐
              ▼              ▼                     ▼
      ┌───────────────┐   ┌────────────────┐   ┌──────────────────┐
      │ A ConfigContract│  │ B RequestMap   │   │ C GateCheck      │
      │ 契约校验       │   │ 参数解剖表      │   │ 前置开关检查      │
      └───────────────┘   └────────────────┘   └──────────────────┘
              │                    │                     │
              ▼                    ▼                     ▼
       XML 与字段是否对齐     这次会给过去什么数据      这次调用会不会真的发请求
```

### A. ConfigContract —— 契约校验

**输入**：`TemplateConfig`（复用插件解析结果）、`InParams` 属性清单（反射）、`RequestMap`（B 的产物）
**不自己解析 XML** —— 一旦自己解析，就等于复制了一份规则，`IsUserEdit`、解密、判重这些细节
迟早和插件走偏。**复用插件的 loader 是这个设计的地基。**

产出四类问题：

| 类别 | 判定 | 后果 |
|---|---|---|
| `MissingInXml` | InParams 属性有、XML 无对应 Code | 该参数恒为 `null`/`false`，接口 body 里是空值 |
| `UnknownInXml` | XML 有 Code、InParams 无同名属性 | 配了但永远不生效（就是 1.5 的横杠问题） |
| `ValueNotParsable` | bool 项的值不是 `"1"`/`"0"`；int 项（如 `Timeout`）不是数字 | 静默 false，或 getter 抛异常 |
| `DuplicateCode` | 同一 Code 出现多次 | 后者覆盖前者，容易误判 |

再加一列 **`UsedBy`**：这个 Code 被哪些接口方法读过。
这一列的价值在于回答"我把 `LineName1` 改成 XX，会影响哪几个接口"。

### B. RequestMap —— 参数解剖表

对每个接口方法，产出"请求字段 → 来源"的映射。来源只有四类：

| 来源类型 | 含义 | 能否靠 XML 改 |
|---|---|---|
| `Xml` | 直接来自某个 XML Code | 能 |
| `XmlByLane` | 按轨道号从 `Xxx1`/`Xxx2` 中选一个 | 能（但要改对轨道那一个） |
| `Runtime` | 来自 `BarCodeTree` / `BoardPCB` 等运行时对象 | 不能 |
| `Constant` | 插件内写死或本地生成（如 `DateTime.Now`） | 不能 |

**这张表怎么来**：不是靠读文档，是靠扫 IL。
现有脚本已能对任一方法列出 `newobj` 的实体类型 + 每个 `set_XXX` 前面压栈的来源，
已经完整跑通 `GetBadMark` / `BarCodeCheck` / `LoginCheck` 三个方法（见第 3 节）。

**产物形态**：一次性离线生成 → 落成 `Config\RequestMap\{插件}.{方法}.json` → 运行时只读这个 json。

这样做的理由：
- 插件版本变了，重跑一次生成器即可，不用改代码；
- 生成器不可能 100% 猜对语义（比如"按轨道选"是 `InParamsLane.Side(lane)` 这种间接调用），
  所以 json 允许人工修订，改完就是权威版本，可以进版本管理；
- 运行时不做 IL 扫描，零开销、零反射解析风险。

### C. GateCheck —— 前置开关检查

有些方法是"开关不开就静默 return"，这比报错更难受：**你以为在测，其实什么都没发**。

已确认的三处（IL 首段就有）：

| 方法 | 前置条件 | 不开的后果 |
|---|---|---|
| `BarCodeCheck` | `IsEnableBarcodeCheck == 1` | 直接返回，不发请求 |
| `LoginCheck` | `IsEnableLoginCheck == 1` | 直接返回，不发请求 |
| `GetBadMark` | `IsReadBadMarkFile == 0` 才走 HTTP | 等于 1 时改读本地 `BoardInfo_*.stf`，不发请求 |

设计上，这些条件写进 `RequestMap` 的 `Gates` 字段，执行前先跑一遍，
不满足就**红字说明原因**，而不是让用户对着"没反应"猜。

## 3. GetBadMark 打样：客户参数到底有几个

由 IL 反推的完整字段来源（AOI / DefaultMES）：

| 请求字段 | 来源类型 | 来源表达式 | XML Code |
|---|---|---|---|
| `BarCode` | Runtime | `BarCodeTree.BarCode` | — |
| `CarrierBarcode` | Runtime | `BarCodeTree.ExtendBarcode` | — |
| `MachineName` | **Xml** | `InParams.MachineName` | `MachineName` |
| `Operator` | **Xml** | `InParams.Operator` | `Operator` |
| `Side` | **XmlByLane** | `InParamsLane.Side(lane)` → `Side1`/`Side2` | `Side1` / `Side2` |
| `JobName` | Runtime | `BarCodeTree.JobName` | — |
| `LineName` | **XmlByLane** | `InParamsLane.LineName(lane)` → `LineName1`/`LineName2` | `LineName1` / `LineName2` |
| `WorkStation` | **XmlByLane** | `InParamsLane.WorkStation(lane)` → `WorkStation1`/`WorkStation2` | `WorkStation1` / `WorkStation2` |
| `GroupBarCode` | Runtime | `BarCodeTree.BoardBarCode` 过滤 `IsValidBarcode` | — |
| `ArrayBarCode` | Runtime | `BarCodeTree.ArrayBarCode` 去重过滤 | — |

**这张表最有价值的一行结论**：
`GetBadMark` 里真正由 XML 决定的"客户参数"只有 **5 个逻辑项 / 7 个 Code**
（`MachineName`、`Operator`、`Side1|Side2`、`LineName1|LineName2`、`WorkStation1|WorkStation2`），
其余 5 个字段（BarCode、CarrierBarcode、JobName、GroupBarCode、ArrayBarCode）
**全部来自 runtime 的 `BarCodeTree`，改 XML 没用**。

同时 `GetBadMark` 还隐性消费 4 个 XML 项（不进 body，但影响行为）：

| XML Code | 作用 |
|---|---|
| `InterfaceUrl` | 拼接接口地址 |
| `Timeout` | 网络超时 |
| `IsReadBadMarkFile` | 1 = 走本地文件，不发 HTTP |
| `IsNgAsBadMark` | 影响返回结果里 BadMark 的判定 |

### 3.1 运行时参数：`BarCodeTree` 怎么造

类型在 **`QuickMiddle.MES.SDK`**（不是 `SinicTek.SDK`），`QuickMiddle.SDK.BarCodeTree`，
有 public 无参构造，**9 个属性全部可写**：

| 属性 | 类型 | 影响 GetBadMark 的哪个字段 |
|---|---|---|
| `StartTime` | DateTime | 只影响日志文件名 |
| `LaneNo` | int | **决定取 `Side1/2`、`LineName1/2`、`WorkStation1/2` 中的哪一个** |
| `JobName` | string | `body.JobName` |
| `BarCode` | string | `body.BarCode` |
| `ExtendBarcode` | string | `body.CarrierBarcode` |
| `ArrayBarCode` | `ArrayBarCode[]` | `body.ArrayBarCode` |
| `BoardBarCode` | `string[]` | `body.GroupBarCode` |
| `JobNum` / `IsMorePart` | string / bool | GetBadMark 不读 |

`ArrayBarCode` 类同样有 5 个可写属性：`ID` / `BoardBarCode` / `BarCode` / `RowIndex` / `ColumnIndex`。

**三个必须避开的坑**（都有 IL 依据）：

1. **两个数组不能留 `null`**。插件里直接对 `BarCodeTree.BoardBarCode` 和 `.ArrayBarCode` 做 LINQ，
   `null` 会抛 `ArgumentNullException`，被插件 try/catch 吞成一句"异常"。**必须先赋空数组。**

2. **条码会被静默过滤**。`UtilBarCode.IsValidBarcode` 的完整逻辑（IL 解出来的）：

   ```
   if (string.IsNullOrWhiteSpace(b))            return false;
   if (b.ToUpper() == "NOREAD")                 return false;
   if (b.ToLower().Contains("globalbarcodeempty")) return false;
   return true;
   ```

   所以 `""`、`"NOREAD"` 这类填进去会被丢掉，最后 `GroupBarCode` 是空数组。**用普通字符串。**

3. **`LaneNo` 决定一切轨道相关字段**。填 2 就必须保证 XML 里 `Side2`/`LineName2`/`WorkStation2`
   有值，否则 body 里对应字段是空串。

**Fixture 设计**：不要写死在按钮里，用 pattern + 序号，避免 MES 端判重复条码：

```json
{
  "LaneNo": 1,
  "JobName": "JOB-TEST-01",
  "BarCodePattern": "PCB-{seq:D4}",
  "ExtendBarcodePattern": "CAR-{seq:D4}",
  "BoardBarCodeCount": 1,
  "ArrayBarCodeCount": 4
}
```

界面上只暴露三个最常改的（`LaneNo` / `BarCode` / `JobName`）。组装完先跑一遍 `IsValidBarcode`
模拟校验，把会被过滤掉的条码红字列出来，不要等请求发出去才发现是空数组。


这也说明"客户参数"和"接口入参"不是一回事：**能进 body 的是 7 个 Code，影响行为的是 4 个**。
两个清单都要显示，否则排查时会漏。

## 4. 界面呈现建议

不做新窗体，在现有 AOITest 主界面加一个"配置契约"分页，三个区：

**上区 · 配置概览**
- 当前 `ConfigCode`（下拉，列出 `Config\Setting\*.config` 的文件名）
- 实际加载路径（把 `MesCustomConfigBaseDirPath` 打出来，路径不对一眼可见）
- 加载结果：`Name`、`TemplateParamSettings.Count`

**中区 · 契约校验（A）**
- 一张表：`Code | Name | Value | IsUserEdit | 是否被 InParams 消费 | UsedBy 方法 | 状态`
- 状态列用颜色：正常 / 缺失 / 多余 / 值非法 / 重复
- 顶部一行汇总：`62 对齐 / 1 多余 / 1 缺失 / 0 值非法`

**下区 · 参数解剖（B + C）**
- 左侧方法列表（来自 B 的 json）
- 右侧选中方法的字段来源表（第 3 节那张表）
- 底部 `Gates` 区：列出该方法的前置条件及当前实际值，不满足标红

**Dry Run 按钮**：不执行方法，只按 B 的表组装并显示预计 body 的 JSON。
拿去和 Apifox 里配的接口字段对照 —— 这就是"我给过去的数据"的最终答案。

## 5. 落地顺序

| 步 | 内容 | 依赖 | 验证方式 |
|---|---|---|---|
| 1 | 打通注入：`LoadTemlateConfig` + 反射写 `BaseParams._InConfig` | 无 | 界面能显示 `TemplateParamSettings.Count == 64` |
| 2 | A 契约校验（只读表格） | 1 | 复现 `ExportDataPathRule-1/-2` 这两条告警 |
| 3 | B 生成器（离线）+ 落 json | 无（可并行） | 生成的 `GetBadMark.json` 与第 3 节表一致 |
| 4 | B 运行时读取 + 参数解剖表界面 | 1、3 | 表里 `MachineName` 的当前值 = XML 里的值 |
| 5 | C GateCheck | 4 | 把 `IsEnableBarcodeCheck` 改 0，界面标红且说明原因 |
| 6 | Dry Run 出 body | 4 | 与插件日志里的 `strJson` 逐字段对比 |

第 1 步是唯一的硬门槛，验证方法：把 XML 里 `MachineName` 改成 `TEST-1234` → 重新注入 →
读 `InParams.MachineName` 应等于 `TEST-1234`。**如果第 1 步过了，后面全是只读展示，风险很低。**

## 6. 边界与风险

1. **不要试图写 `InParams` 的属性**。64 个属性 writable = 0（只读表达式属性），反射也写不进去。
   要改值，改 `TemplateConfig.TemplateParamSettings` 里对应 `Code` 的 `Value`，再重新注入。

2. **`App.SettingActiveConfig()` / `App.InConfigName` 有副作用**：会 `SaveSettings` 把"当前激活配置"
   持久化写进现场设置。AOITest 只读诊断时不要用它，用 1.8 的注入方式。

3. **配置目录是写死的 `D:\EYAOI\MesCustom\Bin\Config\Setting\`**（1.4）。
   所以不在装有 EYAOI 的机器上跑不起来；实验配置要在该目录**新增**文件，不能改已有文件。

4. **RequestMap 的生成器只在开发期用**。它依赖 IL 解析和反射加载插件，
   放到运行时既慢又容易被安全策略拦（反射加载 DLL 在部分环境会被阻止）。

5. **AOI 与 SPI 的 `SinicTek.SDK` 冲突**（同名同版本、成员不同）：
   `RequestMap` 必须以 `{插件DLL}×{方法}` 为主键，不能只按方法名，
   否则 AOI 和 SPI 的同名方法会互相覆盖。
